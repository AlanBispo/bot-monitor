# Price Monitor Bot — Functional and Technical Specification

## 1. Objective

Build a complete local, personal bot for unified product discovery and price monitoring.

The system must allow the user to:
- search for products by name;
- search multiple store-native and web discovery sources through one user command;
- validate, normalize, deduplicate, and rank discovered offers;
- identify the lowest reliable effective price among the offers successfully discovered and
  validated;
- register products from discovered results;
- register a product directly by URL when applicable;
- monitor prices periodically;
- compare the current price against a user-defined target price;
- consider product price, shipping, and discounts/coupons when reliable;
- keep a price history over time;
- send alerts directly to the user through Telegram;
- support queries and commands through Telegram;
- run locally on the user's computer;
- remain simple and easy to maintain.

This project is intended for personal and local use. It must not be designed as a distributed or high-scale system.

## 2. Principles

### 2.1 Simplicity First

Do not add technologies unless they provide a concrete benefit for this use case.

Avoid unless a concrete requirement justifies them:
- microservices;
- Redis;
- distributed queues;
- Kubernetes;
- PostgreSQL;
- web frameworks without a clear need;
- web dashboards;
- mandatory paid external services;
- cloud infrastructure;
- VPS hosting.

### 2.2 Local Execution

The system must work while the user's computer is powered on and has internet access.

The primary environment may be Windows with local Python execution or Python running through WSL, as long as the final setup is documented and functional.

When the computer is turned off, monitoring may stop.

When the computer starts again, the system must be able to start manually and may later be automated.

The code structure may evolve as needed, but it must remain simple and modular.

## 4. Architecture

The application must be a modular Python monolith.

Expected responsibilities:
- Telegram interface;
- periodic monitoring;
- deterministic search-query parsing;
- a unified discovery orchestrator;
- store-native search providers;
- generic web discovery providers;
- per-store offer validation adapters;
- conservative generic structured-data extraction for otherwise unsupported public stores;
- product identity matching, deduplication, and deterministic offer ranking;
- pricing rules;
- alert rules;
- SQLite persistence;
- history;
- configuration;
- tests.

The physical module layout may vary as long as responsibilities remain separated and unnecessary complexity is not introduced.

## 5. Discovery Flow

The user must be able to search for a product through Telegram using a product name and optional
explicit constraints such as model, capacity, size, condition, and maximum price.

Expected flow:
1. parse the request with deterministic rules into a structured search query, preserving the
   original text;
2. search configured store-native and generic web discovery providers in parallel;
3. collect candidate product URLs without trusting snippet prices as authoritative;
4. validate candidate URLs and redirects before access;
5. route each candidate to its store adapter or to the conservative generic extractor;
6. fetch and normalize current title, variant, seller, availability, product price, shipping,
   confirmed discounts, possible discounts, and canonical URL when available;
7. match equivalent products and keep materially different variants separate;
8. deduplicate the same listing discovered through multiple sources;
9. rank reliable offers by deterministic effective-price rules;
10. present results with source coverage, uncertainty, and failures made explicit;
11. allow the user to confirm one or more listings, define a target price, and start monitoring.

The result called "lowest price" must mean the lowest reliable effective price among the offers
successfully discovered, validated, and matched during that search. The system must not claim to
have found the lowest price on the entire internet.

Broad search must not be repeated on every monitoring cycle.

## 6. Broad Search and Monitoring

### 6.1 Broad Search

Broad search should happen mainly:
- during initial registration;
- when explicitly requested by the user;
- during occasional low-frequency rediscovery, if that feature is implemented.

Objectives:
- find new offers;
- find new pages for the same product;
- detect new sellers or relevant stores.

A broad search must combine, when configured:
- direct search in supported stores;
- a generic web discovery provider that returns candidate URLs;
- optional low-frequency rediscovery for already monitored products.

Search providers only discover candidates. Prices from search snippets, advertisements, or cached
results must not be used as validated prices.

The search response must report:
- which sources completed successfully;
- which sources failed or timed out;
- how many candidates were discovered and validated;
- which results have unknown shipping or other material uncertainty;
- whether some results were excluded because product identity was ambiguous.

### 6.2 Periodic Monitoring

After registration, the system must monitor specific previously confirmed URLs or listings.

Reasons:
- greater stability;
- lower resource consumption;
- lower blocking risk;
- fewer irrelevant results;
- lower traffic;
- lower complexity.

## 7. Stores

Required first complete-release stores:
1. Amazon;
2. Mercado Livre;
3. Magalu.

All three must support direct product-page monitoring. Store-native broad search should be
implemented where it is reliable. A generic web discovery provider must supplement direct store
search and may discover additional public stores.

Additional stores may be added through new adapters. Public pages from otherwise unsupported
stores may be accepted only through a conservative generic extractor when standardized product
data is present and passes validation. Unverified candidates may be shown separately but must not
be included in the reliable cheapest-offer ranking.

Each store must have an isolated integration through an adapter boundary or equivalent abstraction.

The application must not depend on a store's internal details outside its corresponding integration.

## 8. Collection Strategy

The implementation must prefer the simplest reliable solution available.

Preferred order:
1. suitable public or official API;
2. HTTP request and HTML parsing;
3. standardized structured data such as valid product/offer JSON-LD on public pages;
4. browser automation only when necessary and explicitly enabled for a store.

Do not use browser automation for every store by default.

Reasons:
- higher resource usage;
- lower speed;
- higher maintenance cost;
- greater blocking risk.

### 8.1 Discovery Providers

Discovery providers and offer validators are separate responsibilities.

A discovery provider may use:
- a store's official search API;
- a store's public search page;
- a configurable web-search API or self-hosted search service;
- another lawful source that returns public candidate URLs.

A discovery provider result is never sufficient by itself to create price history or trigger an
alert. The candidate page must be validated by an offer adapter.

No implementation may scrape a general search engine in violation of its terms or attempt to
bypass CAPTCHA, authentication, or access controls. A paid provider may be supported as an
optional configuration, but the application must retain a documented no-paid-service path.

### 8.2 Offer Validation and Ranking

Store-specific adapters remain necessary because stores differ in APIs, HTML, variants, seller
models, availability, shipping, coupons, redirects, and anti-automation behavior.

The user sees one combined result list. The discovery orchestrator hides adapter boundaries from
normal use while preserving store-specific isolation internally.

Ranking must be deterministic:
1. compare only candidates matched to the requested product and variant;
2. place reliable effective prices first, in ascending order;
3. keep unknown-shipping offers outside the guaranteed cheapest position;
4. present conditional possible prices separately from guaranteed prices;
5. use a stable tie-breaker such as store name and canonical URL.

### 8.3 Deterministic Query Parsing and Product Matching

The complete product must not depend on AI, an LLM, embeddings, or another generative model.

Query parsing must be deterministic and testable. At minimum it must:
- preserve the original query;
- normalize whitespace and harmless punctuation without destroying model identifiers;
- retain quoted phrases when supported by the provider;
- recognize explicit numeric-unit pairs such as storage, volume, size, and package quantity;
- recognize explicit maximum-price and condition filters when present;
- enforce a documented maximum query length and reject empty input;
- produce a stable structured representation for the same input.

The orchestrator may create a small bounded set of rule-based query variants, but it must always
include the original user terms and must not broaden the search so far that the requested model or
variant is lost.

Product matching must be deterministic and explainable. It must:
- normalize titles and structured attributes;
- treat conflicting model numbers, capacities, sizes, package quantities, and conditions as hard
  mismatches when those attributes are explicit;
- use structured store metadata before title heuristics;
- use a documented lexical score only after hard constraints pass;
- classify candidates as matched, ambiguous, or rejected;
- exclude ambiguous and rejected candidates from the reliable cheapest-offer ranking;
- preserve a reason code that can be displayed and tested;
- allow the user to manually confirm an ambiguous candidate without changing the original data.

No heuristic may fabricate missing product attributes. A missing attribute is unknown, not a
match or mismatch, until another reliable field resolves it.

## 9. Product and Listing

Product and listing are different entities.

A product represents the item the user wants to track.

A listing represents a concrete offer from a store.

A product may have multiple listings.

Each listing:
- belongs to a product;
- belongs to a store;
- has its own URL when applicable;
- keeps its own history;
- can be enabled or disabled.

## 10. Database

SQLite is the default database.

Do not migrate to another database without a real need.

Its usage must be appropriate for local execution and low volume.

WAL mode may be used if it provides a concrete benefit without adding unnecessary complexity.

## 11. Persisted Data

### 11.1 Products

Each product must store at least:
- identifier;
- name;
- normalized identity fields when known, such as brand, model, variant, capacity, color, and
  condition;
- original search request or registration source when applicable;
- target price;
- active/inactive state;
- relevant creation and update timestamps.

### 11.2 Listings

Each listing must store at least:
- identifier;
- related product;
- store;
- URL or equivalent identifier;
- canonical URL when available;
- title;
- seller when available;
- discovery source;
- validation status and relevant uncertainty flags;
- active/inactive state;
- relevant timestamps.

### 11.3 Price History

Each valid check must create a new snapshot.

Each snapshot must be able to represent, when available:
- listing;
- product price;
- shipping;
- confirmed discount;
- possible discount;
- effective price;
- possible effective price;
- availability;
- seller;
- capture date and time.

### 11.4 Alerts

The system must persist enough information about sent alerts to prevent spam and improper duplication.

### 11.5 Search Sessions

The system must persist enough search-session information to let the user select a displayed
result without resubmitting arbitrary text or copying a long URL.

A search session should store, with bounded retention:
- identifier and authorized chat;
- original and structured query;
- start and completion timestamps;
- source coverage and failures;
- normalized candidate references and their displayed ordering;
- validation and product-match status.

Search-session retention must be configurable or cleaned automatically so temporary discovery
data does not grow without bound. Search history must never be treated as price history.

## 12. Price History

Price history is append-only.

A new valid observation creates a new snapshot.

Previous snapshots must not be overwritten during normal updates.

The history must support retrieving:
- current price;
- lowest recorded price;
- highest recorded price;
- average price;
- lowest price within a time window;
- per-store history;
- consolidated product history.

Charts may be added later.

## 13. Effective Price

The system must not compare only the displayed product price.

The effective price must consider:
- product price;
- known shipping cost;
- confirmed discounts.

The target price should preferably be compared against the reliable effective price.

Unknown values must not be invented.

## 14. Coupons and Discounts

Not every discovered discount should be treated as guaranteed.

The system must distinguish confirmed discounts from conditional or uncertain discounts.

Examples of conditions:
- account-specific eligibility;
- Prime subscription;
- app-only use;
- first purchase;
- eligibility rules;
- targeted coupons.

Only discounts that are clearly applicable may be included in the guaranteed effective price.

Conditional discounts may be presented as a possible price, with uncertainty clearly indicated.

The system must not present a conditional price as guaranteed.

## 15. Shipping

Whenever possible, shipping must be included in the calculation.

If shipping cannot be determined automatically:
- do not invent a value;
- record it as unknown;
- make the uncertainty explicit;
- do not assume free shipping.

If shipping depends on location or postal code and cannot be obtained reliably, this must be reported.

## 16. Alerts

The minimum required alert is the target-price alert.

The condition is that the reliable effective price is less than or equal to the target price.

Additional alerts may exist, such as:
- new historical low;
- significant percentage drop;
- another store becoming significantly cheaper.

These additional alerts are optional.

### 16.1 Spam Prevention

The system must not repeatedly send the same alert without a relevant change.

The policy may be simple as long as it prevents spam and remains predictable.

## 17. Telegram

Telegram is the primary interface.

The bot must:
- receive commands;
- reply in the private conversation;
- send automatic alerts;
- restrict control to the authorized user.

Desired capabilities:
- search for a product by command with optional explicit filters;
- see one combined, price-ordered result list with store and uncertainty information;
- select a result by a short result identifier or Telegram button;
- add or confirm a product/listing;
- attach multiple equivalent offers to the same monitored product;
- list monitored products;
- force a check;
- query history;
- remove or disable monitoring;
- query status;
- get help.

Exact command names may vary as long as these capabilities exist.

## 18. Telegram Security

The system is intended for personal use.

There must be a simple and consistent way to restrict access.

At minimum:
- accept commands only from the configured authorized chat;
- safely reject or ignore other chats;
- keep the bot token out of version-controlled code;
- load secrets from the environment or an equivalent secure configuration mechanism.

The full token must never appear in logs.

## 19. Configuration

Secrets and variable options must be configurable outside the source code.

Configuration must cover at least:
- bot token;
- authorized chat;
- check interval;
- database path.
- enabled stores and discovery providers;
- provider credentials when an optional provider requires them;
- request, search, and per-source timeouts;
- bounded discovery concurrency and candidate limits;
- postal code or location only when the user explicitly configures it for shipping calculation;
- generic-store extraction enable/disable state;
- browser automation enable/disable state per store.

An example configuration file without real secrets must exist.

Real environment files containing secrets must remain outside version control.

## 20. Scheduler

The same process may:
- keep the Telegram bot active;
- run periodic checks.

Separate services are not required for these responsibilities.

The monitoring frequency must be configurable.

Broad rediscovery, if implemented, must run significantly less often than direct monitoring.

## 21. Local Startup

The system must be prepared for local execution.

The first functional delivery does not depend on operating-system startup automation.

Automatic startup may later be configured through Windows or WSL mechanisms.

That automation must not require changes to the application's core logic.

## 22. Logs

Logs must be simple and useful.

When relevant, they should record:
- startup;
- search-session identifiers and source coverage;
- checks;
- store errors;
- relevant price changes;
- sent alerts;
- temporary failures;
- parsing failures.

They must not record:
- Telegram tokens;
- secrets;
- sensitive cookies;
- authentication headers;
- credentials.

## 23. Error Handling

Failure in one store must not bring down the entire monitoring process when other stores can continue.

Failure in one search source must not discard valid results from other sources. A partial search
must be labeled partial instead of being presented as complete.

Transient errors must:
- be logged;
- preserve previously valid data;
- not create fake or zero prices;
- not trigger false alerts.

## 24. Price Validation

The system must not silently accept the following as valid prices:
- zero when caused by a parsing failure;
- negative values;
- empty text;
- clearly incompatible values without validation;
- installment amounts as if they were full prices;
- discount percentages as prices;
- shipping values as product prices.

Monetary parsing must be tested.

## 25. URL Security

The system receives and accesses URLs and must treat them as untrusted input when they come from the user or external sources.

Requirements:
- accept only supported web schemes;
- identify whether a URL belongs to a dedicated supported-store adapter or the generic extractor;
- apply the same network-safety controls to URLs returned by web discovery providers;
- block local file access;
- prevent improper loopback access;
- prevent improper access to private and link-local networks;
- prevent access to metadata endpoints;
- account for redirects during validation;
- do not execute retrieved content;
- do not build shell commands from URLs or Telegram messages.

## 26. Dependencies

Prefer dependencies that are known, maintained, and necessary.

Before adding a new dependency, verify whether the standard library or an existing dependency can adequately solve the problem.

Avoid adding dependencies for trivial functionality.

## 27. Tests

The project must include automated tests.

Expected functional coverage includes, when applicable:

### Pricing
- product plus shipping;
- product plus shipping minus discount;
- possible discount not treated as guaranteed;
- unknown shipping;
- invalid value;
- monetary rounding;
- price equal to target.

### Alerts
- price above target;
- price equal to target;
- price below target;
- duplicate alert;
- relevant price change.

### Database
- product creation;
- listing creation;
- price snapshot;
- history query;
- deactivation;
- alert persistence;
- history preservation.

### Security
- unauthorized chat;
- invalid URL;
- unsupported scheme;
- local or private target blocked;
- secret not present in logs.

### Store Adapters
Whenever possible, parsing should be tested with deterministic fixtures instead of depending on live internet access.

Required cases include:
- successful and empty store-native search;
- blocked, timed-out, and changed-page responses;
- unavailable products and stale displayed prices;
- explicit and ambiguous shipping;
- canonicalization and duplicate URLs;
- one source failing while other sources return usable results.

### Discovery and Matching
- one command fan-out to multiple providers;
- candidate validation before ranking;
- snippets never accepted as authoritative prices;
- exact-product matching and separation of different variants;
- stable structured-query output for equivalent normalized input;
- hard mismatches for conflicting model, capacity, size, package quantity, or condition;
- ambiguous matches excluded from reliable ranking until user confirmation;
- matching reason codes preserved and presented;
- deterministic deduplication and ordering;
- reliable effective prices ordered before unknown-shipping offers;
- partial-source coverage disclosed to the user;
- bounded candidate count and search-session retention.

### Query Parser
- empty, oversized, and malformed query rejection;
- quoted terms and model identifiers preserved;
- explicit maximum-price and condition filters;
- storage, volume, size, and package-quantity units;
- bounded rule-based query variants;
- no AI service or model required at runtime.

## 28. Quality Tools

The project must keep tests and linting configured.

Type checking, static security analysis, and dependency vulnerability analysis should be used when configured and useful.

Relevant security failures must be fixed before the implementation is considered approved.

## 29. Complete Product Scope

The complete first release must include:
1. functional and authorized Telegram interaction;
2. SQLite persistence and bounded search-session storage;
3. unified multi-source search with transparent partial-result reporting;
4. a configurable generic web discovery provider with a documented no-paid-service path;
5. end-to-end offer validation and monitoring for Amazon, Mercado Livre, and Magalu;
6. conservative generic extraction of standardized product data from additional safe public
   store pages, with unverified results excluded from guaranteed ranking;
7. product identity and variant matching, deduplication, and deterministic effective-price
   ranking;
8. direct URL registration and attachment of multiple listings to one product;
9. periodic direct-listing monitoring without repeated broad search;
10. reliable price, shipping, discount, availability, history, and alert behavior;
11. installation, configuration, manual startup, and optional automatic-start documentation for
    Windows/WSL;
12. automated tests, linting, security checks, and dependency checks;
13. safe degradation when stores, discovery providers, or Telegram fail.

Implementation may be delivered in reviewed increments, but the project must not be described as
complete until every item above satisfies the Definition of Done.

## 30. Out of Scope and Non-Goals

Do not implement without a later explicit request:
- web dashboard;
- mobile application;
- multi-user authentication;
- payments;
- cloud infrastructure;
- VPS;
- Kubernetes;
- microservices;
- distributed queue;
- remote database;
- aggressive scraping;
- CAPTCHA bypass;
- techniques intended to circumvent store protection mechanisms.

The following are explicit non-goals:
- guaranteeing the lowest price across the entire internet;
- treating search-engine snippets as current authoritative offers;
- requiring or integrating an AI model, LLM, embedding model, or generative agent;
- monitoring every discovered candidate before user confirmation;
- defeating authentication, rate limits, CAPTCHAs, or anti-bot controls.

## 31. Definition of Done

An implementation should only be considered complete when:
- it complies with this specification;
- it runs locally;
- relevant tests pass;
- linting passes;
- no secrets are committed;
- no known blocking vulnerability remains;
- the bot restricts control to the authorized user;
- one user search produces a unified result from all successfully completed configured sources;
- source failures and unknown shipping are visible in the result;
- Amazon, Mercado Livre, and Magalu work end-to-end for discovery or discovered-URL validation,
  registration, direct monitoring, history, and alerts;
- every ranked price comes from a freshly validated offer rather than a snippet;
- materially different product variants are not silently compared as equivalent;
- query parsing, product matching, deduplication, and ranking are deterministic and covered by
  repeatable tests;
- the installed application has no runtime dependency on an AI or model service;
- history is persisted correctly;
- periodic monitoring does not perform broad search on every cycle;
- alerts do not generate improper spam;
- failure in one store does not unnecessarily bring down others;
- execution documentation is up to date.

## 32. Decision Rule

When choosing between a simple solution and a more sophisticated one, choose the simple solution as long as it is:
- correct;
- secure;
- testable;
- compatible with this specification;
- easy to maintain locally.

## 33. Single Delivery and Final Review

The implementation must be completed as one cohesive delivery. The operational workflow must use
one Coder execution for the complete scope, followed by one Finalizer execution that reviews the
whole result, fixes every confirmed defect, runs the required validation, and delivers the final
status. The work must not be split into separate implementation gates or repeated agent loops.

### 33.1 Complete Implementation Scope

The single implementation delivery must:
- reject malformed monetary formats instead of normalizing them into plausible prices;
- classify explicit, ambiguous, and unknown availability safely so unavailable products cannot
  create target-price alerts;
- preserve append-only history and duplicate-alert prevention.

It must also implement and test:
- the structured deterministic query model;
- discovery-provider and offer-validator boundaries;
- bounded parallel fan-out with per-source timeouts;
- search sessions and short result identifiers;
- candidate canonicalization, matching, rejection, ambiguity, deduplication, and ranking;
- partial-result reporting.

Tests for the orchestrator must use deterministic fake providers and must not require live store
access.

The delivery must complete Amazon, Mercado Livre, and Magalu adapters for direct product
validation and monitoring. It must implement store-native discovery where reliable and ensure
generic web discovery can still route a discovered URL to the correct adapter.

Each adapter must have deterministic fixtures for successful, unavailable, malformed, blocked,
and changed-page cases. One adapter failure must not suppress valid results from the others.

The delivery must implement at least one configurable generic web discovery provider and document
its setup, limits, and terms-sensitive operational requirements. It must implement the
conservative generic structured-data extractor for safe public store pages.

The final review must verify that:
- discovered URLs pass URL and DNS safety checks before access;
- redirects are revalidated;
- snippet prices never enter history, ranking, or alerts;
- generic extraction fails closed when product, offer, currency, availability, or full price is
  ambiguous;
- unsupported and unverified results are clearly separated from reliable ranked offers.

The delivery must implement the complete user flow:
1. submit one `/buscar` command;
2. receive a combined result list ordered by reliable effective price;
3. see source coverage, partial failures, unknown shipping, and ambiguous variants;
4. select a result by short identifier or button;
5. set or confirm the target price;
6. register one or more equivalent listings;
7. force a direct check and query history.

Long responses must remain within Telegram limits, and expired search-session selections must fail
with a clear instruction to search again.

Before the single delivery is called complete:
- the scheduler must monitor only confirmed listings;
- broad rediscovery must be separately configured and lower frequency;
- concurrency, response size, redirects, retries, and timeouts must be bounded;
- installation, configuration, operation, automatic startup, backup, and troubleshooting must be
  documented;
- the complete test suite, linting, static security analysis, and dependency audit must pass;
- no real secret may exist in source, fixtures, documentation, logs, or generated artifacts;
- the Finalizer must leave no known blocking finding after its corrections.

### 33.2 Mandatory End-to-End Acceptance Scenario

The automated acceptance suite must prove a scenario in which:
- a query requests a specific model and capacity;
- three sources return a duplicate listing, a different-capacity variant, valid equivalent offers,
  an unknown-shipping offer, and one source timeout;
- the duplicate is collapsed;
- the different variant is rejected with a reason;
- the timeout is reported as partial coverage;
- the known-shipping equivalent offers are ranked by effective price;
- the unknown-shipping offer is displayed but not called the guaranteed cheapest;
- the user selects a result and registers the listing;
- a later monitoring cycle requests only the saved listing URL;
- a valid target-price observation creates history and at most one appropriate alert;
- repeating the same observation does not send a duplicate alert.

The scenario must use controlled fixtures or fake transports and must not depend on live internet,
current store HTML, or any AI/model service.
